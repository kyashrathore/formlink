# LLD & Migration Plan: Refactoring the Core Question Schema (Cutoff Strategy)

## 1. Executive Summary & Goal

**The Problem:** Our current `QuestionSchema` separates semantic intent (`questionType`) from presentation (`display.inputType`). This forces us to maintain a complex, brittle, and hard-to-read `superRefine` validation block to enforce the constraints between them.

**The Goal:** To refactor the `QuestionSchema` into a more robust, type-safe, and self-documenting structure. We will unify the type and display properties into a single, discriminated `type` object.

**The Strategy: Cutoff Migration.** We have determined that an incremental migration is not necessary. We will perform a direct, "big bang" refactoring. All required code changes will be made in a single feature branch and deployed at once. This is a faster and cleaner approach.

---

## 2. Audit of `questionType` and `inputType` Usage

A codebase-wide search reveals several distinct categories of usage for these two properties. This audit forms the basis of our refactoring checklist.

### Categories of Usage:

1.  **AI Prompt Engineering (`apps/formcraft/app/lib/prompts.ts`):**
    - **Current State:** The system prompts are extremely detailed, instructing the AI on the complex, conditional rules between `questionType` and `inputType`. The AI is forced to act as a validator.
    - **Impact:** This is the area that will benefit most. The prompts will become radically simpler.

2.  **Rendering Logic (`apps/formfiller` & `packages/ui`):**
    - **Current State:** Components use `switch (question.questionType)` to decide which high-level component to render (e.g., a choice component vs. a text input component).
    - **Impact:** These `switch` statements are the primary target of our refactoring. They must all be changed to read from the new `type` object.

3.  **State Management (`apps/formcraft/app/dashboard/forms/[formId]/stores/useFormEditorStore.tsx`):**
    - **Current State:** The Zustand store has actions that create and update questions using the old, flat structure.
    - **Impact:** These actions will need to be updated to construct the new, nested `type` object.

4.  **Data Mapping & Transformation (`apps/formfiller/lib/mappers/schema-to-ui.ts`):**
    - **Current State:** This file contains logic to map the backend schema to a slightly different UI schema, including functions like `getInputTypeForQuestionType`.
    - **Impact:** This mapping logic will be significantly simplified or eliminated, as the new schema is more aligned with the UI's needs.

5.  **AI-Assisted Repair (`packages/schema/src/questionRepair.ts`):**
    - **Current State:** A critical utility, `repairQuestionInputTypes`, exists to fix inconsistencies between `questionType` and `inputType` generated by the AI.
    - **Impact:** This entire file can and **should be deleted**. Its existence is a symptom of the flawed schema. The new schema's inherent type safety makes this repair logic obsolete.

6.  **Analytics (`apps/formcraft/app/lib/analytics.ts`):**
    - **Current State:** Analytics events are fired with `questionType` as a parameter.
    - **Impact:** A simple change to pass `question.type.name` instead.

## 3. The "Target" Schema

This is the ideal state we will implement directly. This is a **purely structural refactoring**. No new properties or features are being added. We are reorganizing the existing properties into a more logical structure.

```typescript
// In packages/schema/src/index.ts

// The new, unified type object. This is a discriminated union.
const QuestionTypeSchema = z.discriminatedUnion("name", [
  // Text-based questions
  z.object({
    name: z.literal("text"),
    format: z.enum([
      "text",
      "textarea",
      "email",
      "url",
      "tel",
      "number",
      "password",
      "country",
    ]),
  }),
  // Choice-based questions
  z.object({
    name: z.enum(["singleChoice", "multipleChoice"]),
    display: z.enum(["radio", "checkbox", "dropdown", "multiSelectDropdown"]),
    options: z.array(OptionSchema),
  }),
  // Rating question
  z.object({
    name: z.literal("rating"),
    config: RatingConfigSchema, // Uses the existing RatingConfigSchema
  }),
  // Date question
  z.object({
    name: z.literal("date"),
    format: z.enum(["date", "dateRange"]),
  }),
  // Ranking question
  z.object({
    name: z.literal("ranking"),
    options: z.array(OptionSchema),
  }),
  // File Upload question
  z.object({
    name: z.literal("fileUpload"),
  }),
  // Address question
  z.object({
    name: z.literal("address"),
  }),
  // Linear Scale question
  z.object({
    name: z.literal("linearScale"),
    config: LinearScaleConfigSchema, // Uses the existing LinearScaleConfigSchema
  }),
  // Likert Scale question
  z.object({
    name: z.literal("likertScale"),
    options: z.array(z.string()),
  }),
]);

// The new, simplified QuestionSchema
export const QuestionSchema = z.object({
  id: z.string().min(1),
  questionNo: z.number(),
  title: z.string(),
  description: z.string().optional(),

  // Base properties from our Classic Mode feature work
  label: z.string().optional(),
  page: z.number().int().optional(),
  styling: z
    .object({ colSpan: z.number().int().min(1).max(12).optional() })
    .optional(),
  isCheckpoint: z.boolean().optional(),

  // The new, unified type property
  type: QuestionTypeSchema,

  // Other base properties that remain at the top level
  validations: QuestionValidationsSchema.optional().default({}),
  conditionalLogic: JSONataConditionSchema.optional(),
  defaultValue: z
    .union([
      /* ... existing types ... */
    ])
    .optional(),
  submissionBehavior: SubmissionBehaviorSchema,
  // ... readableValidations, etc.
});
```

## 4. The Cutoff Implementation Plan

This is the master checklist for the refactoring effort. All steps must be completed within a single feature branch.

### **Step 1: The Schema "Break" (`packages/schema/src/index.ts`)**

This is the first action. It will intentionally cause TypeScript errors across the entire codebase, giving us a perfect to-do list.

1.  **Define the New Types:** Add the new `QuestionTypeSchema` discriminated union as defined above.
2.  **Modify `QuestionSchema`:**
    - Delete `questionType` and `display` from the `BaseQuestionSchema`.
    - Delete the various `...QuestionSchema` extensions (e.g., `ChoiceQuestionSchema`, `RatingQuestionSchema`).
    - Move properties that were on the extensions (`options`, `ratingConfig`, etc.) into their corresponding objects within the new `QuestionTypeSchema`.
    - Add the new `type: QuestionTypeSchema` property to the main `QuestionSchema`.
3.  **Delete the entire `.superRefine(...)` block** from the `QuestionSchema` definition.
4.  **Delete the `questionRepair.ts` file** and remove its export from `index.ts`.

### **Step 2: The `formfiller` Refactor (The Renderer)**

This is a well-isolated and critical part of the work, perfect for our new engineer.

- **Primary Goal:** Fix all TypeScript errors in the `apps/formfiller` directory.
- **Key Files & Actions:**
  - **`lib/mappers/schema-to-ui.ts`:** This file will require significant changes. The logic that maps `questionType` to `inputType` can be removed. The mapping will now be a more direct translation from the new `question.type` object to the `UIQuestion` object.
  - **`components/typeform/TypeFormQuestion.tsx` & `components/chat/QuestionWrapper.tsx`:** The core rendering components. The main `switch` statement in these files will change from `switch (question.questionType)` to `switch (question.type.name)`.
  - **Accessing Properties:**
    - `question.options` becomes `question.type.options` (only available inside the `singleChoice` and `multipleChoice` cases).
    - `question.display.inputType` becomes `question.type.display` (for choice questions) or `question.type.format` (for text questions).
  - **Hooks (`hooks/useTypeFormKeyboard.ts`):** This hook has logic that depends on `questionType`. It must be updated to check `question.type.name`.

### **Step 3: The `formcraft` Refactor (The Editor)**

This is the most complex part of the refactor.

- **Primary Goal:** Fix all TypeScript errors in the `apps/formcraft` directory.
- **Key Files & Actions:**
  - **State Management (`stores/useFormEditorStore.tsx`):** The actions for adding a new question (`addQuestion`) and updating one (`updateQuestion`) are the most critical. They must be rewritten to construct and modify the new, nested `type` object. For example, adding a `singleChoice` question will now involve creating a `type` object like `{ name: 'singleChoice', display: 'radio', options: [] }`.
  - **UI (`components/form/FormEditor/QuestionDetails.tsx`):** The properties panel must be refactored to be driven by `question.type`. The UI for selecting `display` (e.g., radio vs. dropdown) should only appear when `question.type.name` is `singleChoice` or `multipleChoice`.
  - **AI Agents & Prompts (`lib/prompts.ts`, `lib/chat/tools/`):**
    - **Simplify Prompts:** The prompts will be drastically simplified. Remove all the complex instructions about the rules between `questionType` and `inputType`.
    - **Update AI Instructions:** Add new, simpler instructions for the AI to generate the nested `type` object.
    - **Update Tool Schemas:** The Zod schemas that validate the AI's output in the tool files (e.g., `generate-question.ts`) must be updated to expect the new `QuestionSchema`.

Welcome! Your first mission is to lead the refactoring of our entire form rendering application, `formfiller`. By taking ownership of this critical piece of the project, you'll gain a deep understanding of our frontend architecture.
